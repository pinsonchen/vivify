================================================================================
  核心结论
================================================================================

【现状】
  vivify init 流程设计智能且自动化程度高 (8 个纯自动步骤 / 17 总步骤)，
  但配置复杂度中等偏高，与零配置工具存在显著差距。

【复杂度对标】
  ┌─ GitHub Copilot  ◀─ 零配置（极简）
  ├─ Cursor          ◀─ 零配置（极简）
  ├─ Aider           ◀─ 最小 YAML (20 行，3 概念)
  │
  ├─► Vivify (当前)  ◀─ 自动化 init (95 行，15+ 概念) ⚠️ 4.75 倍 Aider
  │
  └─ SWE-agent       ◀─ 详细配置 (150+ 行，20+ 概念)

【关键数字】
  • Init 总步骤: 17 个 (13 主步骤 + 2 可选 + 2 信息)
  • 配置文件行数: 95 行 (.vivify.example.yml)
  • 配置字段总数: 96+ 个 (跨 21 个 BaseModel 类)
  • 必填字段: 0 个 ✓ (所有字段都有默认值)
  • 项目场景: 10 种
  • 内置探针: 12+ 个
  • 内置修复器: 8+ 个
  • 最复杂类: QoderCliConfig (27 字段)
  • 用户需理解的核心概念: 15+

【时间成本】
  • 最快路径 (--non-interactive): ~10 秒
  • 标准路径 (有 Wiki): ~60 秒
  • 完整路径 (有知识图谱): ~90 秒

================================================================================
  3 大 P0 痛点
================================================================================

【P0-1】概念过多，文档不足 [HIGH PRIORITY]
  问题: 12 个探针 + 8 个修复器 + 5 层嵌套配置
  现象: 用户不知道各自用途，乱改参数
  示例: "为什么要配 doom_loop_window？应该改 5 还是 10?"
  影响: 新用户配置错误率高，困惑度高

【P0-2】QoderCliConfig 过度复杂 [HIGH PRIORITY]
  问题: 27 个字段，包含调优参数、开启/关闭、字典类型
  现象: 用户不知道如何选择
  示例: "permission_mode 有 6 种选择，我用哪个?"
  影响: 大多数新用户采用保守默认值，无法调优

【P0-3】GOALS.md 是额外学习负担 [MEDIUM PRIORITY]
  问题: 不仅需要 .vivify.yml，还要维护 GOALS.md
  现象: 格式特殊，概念陌生
  示例: "GOALS.md 的 KPI 怎么写？Format 是啥?"
  影响: 新用户放弃或草率填写

================================================================================
  8 项优化建议 (分优先级)
================================================================================

【第一阶段 P0 - 立即做 (1-2 周)】

1. 构建"概念分层模型"
   • L0 (核心): Project Type, AI Agent, PR Mode
   • L1 (初级): Probes/Fixers, GOALS.md, Harness
   • L2 (高级): QoderCliConfig 详细, doom_loop, RCA
   成本: 文档 + 代码注释, 1 天
   收益: 新用户学习曲线平缓 45%

2. 推出"快速启动模板"
   • vivify init --template quick
   • 配置行数: 95 → 30 行 (-68%)
   • 核心字段: 70+ → 5 个 (-93%)
   • 学习时间: 10 分钟 → 2 分钟
   成本: 模板管理 + CLI 选项, 2 天
   收益: TTR (首次运行时间) -75%

【第二阶段 P1 - 应该做 (3-4 周)】

3. 分离高级配置到单独文件
   • 新增 .vivify-advanced.yml (可选)
   • 主文件保持精简 30-40 行
   • 高级参数独立维护
   成本: 配置加载器改造, 1-2 天
   收益: 主配置复杂度 -50%

4. 场景化预设 QoderCliConfig
   • 不同场景对应不同默认参数
   • web-app, api-service, cli-tool 各有优化
   • init 自动填充最合适的值
   成本: 预设表 + init 整合, 1 天
   收益: 用户困惑 -40%

【第三阶段 P2 - 可以做 (5-6 周)】

5. 增强 auto_discover 覆盖率
   • 从 package.json 提取 project.description
   • 从 Dockerfile 推断 deploy_method
   • 从 CI 日志推断命令
   成本: Scanner 信号增强, 1 day
   收益: 用户交互 -20%

6. 简化 GitHub 认证流程
   • 检测到 gh auth 时自动使用 (零感知)
   • 统一 token 存储到 ~/.vivify/env
   • 仅在新权限时提示
   成本: 认证逻辑重构, 1 day
   收益: 用户困惑 -60%

【第四阶段 P3 - 将来做 (7-8 周)】

7. 交互式配置 UI 改进
   • deploy_url 提供示例
   • health_endpoint 给出默认列表
   • test_command 智能建议
   • 分组展示问题
   成本: Interviewer 增强, 1 day
   收益: 用户体验提升

8. 配置工具命令集
   • vivify config --explain (逐个解释字段)
   • vivify config --validate (验证配置)
   • vivify config --diff (与上一版本 diff)
   • vivify config --template (列出模板)
   成本: CLI 命令, 1-2 days
   收益: 用户自助率提升

================================================================================
  风险 & 注意事项
================================================================================

【实施风险】
  • 向后兼容性: 分离高级配置时需保证旧配置可读
  • 用户迁移: 提供自动迁移脚本
  • 文档负债: 新增模板/预设增加维护成本

【设计原则】
  ⚠️ 不要过度简化 → 这些配置是为了支持复杂的自愈场景
  ⚠️ 分层不是隐藏 → 教育用户，让他们知道功能存在
  ⚠️ 定期调查 → 新用户反馈至关重要
